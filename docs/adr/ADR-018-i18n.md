# ADR-018 — Internationalization

- **Status:** Accepted
- **Date:** 2026-11-01
- **Deciders:** project owner (delegated to Claude Code, autonomous mode)
- **Supersedes / Amended by:** related: §14 **A7** (`Group.locale`, per-member locale and timezone)

## Context

- Groups are global and often **internally multilingual**: a family may mix English and Urdu in the same thread, with one member who prefers Spanish and another in a different timezone. "Pick one group language" is not a real option.
- The bot's replies are generated text, so language is a model behaviour, not a resource-bundle lookup. The dashboard's strings are the opposite: fixed UI copy that needs a translation workflow.
- Retrofitting i18n is expensive and always leaves hardcoded strings behind, so the scaffolding has to exist from the first screen even though launch is English-only.
- Multilingual retrieval and date parsing are separate problems handled elsewhere (ADR-007, ADR-011), but they share the same requirement: non-Latin scripts and code-mixed text are first-class, not an edge case.

## Decision

| Surface | Approach |
|---|---|
| Bot language | **Model-driven.** Village follows each group's and each member's locale, including mixed-language threads. It is a behaviour-charter rule, not a string table |
| Dashboard | **`i18next`** (+ react-i18next) **from day one**, namespaces loaded per route, keys type-checked. **English at launch**, community translations later |
| Per-member settings | **Timezone and locale per member** (A7), used by `Intl` and Temporal for every date, time and number (ADR-011) |
| Templates and copy | Bot message templates, tool descriptions and the behaviour charter live in **versioned template files**, never inline strings (`01` §11.12), so they are localizable and reviewable as copy |

The translation workflow (`13` §3.F.8) that this decision implies: i18next JSON under `apps/dashboard/src/locales/<lng>/`, English extracted in CI, **Weblate** on the libre plan syncing by PR bot, a language shipping at **≥ 90% coverage plus one reviewer**, Starlight i18n with **Lunaria** status tracking for the docs, priority order **member-facing pages and consent copy → quickstarts → concepts**, and machine translation allowed **only** with a fluent human reviewer. English only at launch; the infrastructure is ready at M15.

## Alternatives considered

`01` §2 records **no alternatives** for this ADR. The implementation alternative considered later in the plan is noted for completeness:

| Alternative | Why not |
|---|---|
| **FormatJS** instead of i18next (`09` §2 D-24) | i18next's per-route namespace loading, its React bindings and its Weblate integration fit the SPA and the community-translation workflow directly; FormatJS would need more wiring for the same outcome. |

What was *not* treated as an option: a single bot language, or deferring dashboard i18n until after 1.0. The first contradicts the product's audience; the second guarantees a long tail of hardcoded strings.

## Consequences

**Good**
- A mixed-language family gets replies in the language each message was written in, with no configuration.
- Dates, times and numbers are correct per member, which is the difference between a useful reminder and a wrong one.
- Translations can arrive as community PRs without a refactor, because the keys and the workflow already exist.
- Copy living in versioned template files means it can be reviewed like product copy and localized without touching code.

**Bad / accepted costs**
- Every dashboard string must be a key from the first commit, which is friction on every screen before a single translation exists.
- Model-driven language is not deterministic: it needs eval coverage per language rather than a snapshot test (`M13-T13` includes a multilingual date eval).
- Non-Latin scripts cost real work elsewhere: trigram FTS for CJK/Thai groups (`M13-T11`), and the embedding bake-off's Arabic/Devanagari subset (ADR-007).
- RTL layout support has to be maintained in the dashboard even while launch is English-only.

**Follow-ups**
- `M9` — dashboard i18n wiring and typed keys (`09` §2 D-24).
- `M13-T13` — localized templates and the multilingual date eval.
- `M13-T11` — trigram FTS for CJK/Thai groups.
- `M15` — translation infrastructure ready (Weblate, Lunaria), launch in English.
